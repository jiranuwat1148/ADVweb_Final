**แบ่งงานทีม 4 คน — ระบบจัดเส้นทางและแบ่งงานไรเดอร์ส่งด่วนมื้อเที่ยง**

แผนนี้แบ่งงานทั้ง frontend และ backend สำหรับมินิโปรเจกต์ปี 3 โดยใช้ Node.js + Express + TypeScript + SQLite และ Angular ตามแบบที่วางไว้ ใช้ Figma และ frontend ต้นแบบที่มีแล้วเป็นจุดเริ่มต้น

| สมาชิก | รับผิดชอบหลัก | งานที่ต้องทำ | สิ่งที่ส่งให้ทีม |
|---|---|---|---|
| คนที่ 1 | ฐานข้อมูลและ API จัดการข้อมูล | ออกแบบตารางและความสัมพันธ์ สร้างฐานข้อมูล ข้อมูลตัวอย่าง เข้าสู่ระบบเจ้าของร้าน CRUD ลูกค้าและออเดอร์ จำลองออเดอร์ ตรวจข้อมูลและสถานะก่อนแก้ไข | Schema, seed, API ลูกค้า/ออเดอร์ที่ใช้งานได้ และตัวอย่าง request/response |
| คนที่ 2 | จัดเส้นทางและคำนวณต้นทุน | แบ่งงานไม่เกิน 3 ออเดอร์ต่อใบงาน เรียงลำดับส่ง คำนวณเวลา ระยะทาง ค่าส่งและกำไร สร้างแผนทางเลือก บันทึกและยืนยันแผน สร้างเลขใบงาน ค้นหาใบงานที่ยืนยันแล้ว | API แผนจัดส่ง ใบงานไรเดอร์ และผลตรวจอัลกอริทึม |
| คนที่ 3 | Frontend ภาพรวมและลูกค้า | หน้าภาพรวม ตัวเลขสรุป แผนที่เส้นสี เลือกใบงาน เปรียบเทียบและยืนยันแผน หน้าลูกค้าและฟอร์มพิกัด เชื่อม API และจัดรูปแบบหน้าจอหลัก | หน้าภาพรวมและลูกค้าที่ใช้ข้อมูลจาก backend |
| คนที่ 4 | Frontend ออเดอร์และไรเดอร์ | หน้าเพิ่ม/แก้ไข/ยกเลิกออเดอร์ ค้นหาและกรอง หน้าไรเดอร์บนมือถือ กรอกเลขใบงาน แสดงจุดส่งและปุ่มนำทาง เชื่อม API และประสานการรวมงาน/เดโม | หน้าออเดอร์และใบงานมือถือ พร้อมขั้นตอนรันระบบรวม |

แต่ละคนต้องทดสอบส่วนที่ตัวเองทำและเขียนรายงานส่วนนั้น คนที่ 4 ประสานการรวมงานและรวบรวมรายงาน โดยทุกคนช่วยกันทดสอบระบบครบหนึ่งรอบ

**ขอบเขตไฟล์ควรแบ่งตั้งแต่เริ่ม** เพื่อไม่ให้แก้ไฟล์เดียวกัน:

```text
backend/
  sql/schema.sql                       # คนที่ 1
  sql/seed.sql                         # คนที่ 1
  src/db.ts                            # คนที่ 1
  src/routes/auth.routes.ts            # คนที่ 1
  src/routes/customers.routes.ts       # คนที่ 1
  src/routes/orders.routes.ts          # คนที่ 1
  src/routes/plans.routes.ts           # คนที่ 2
  src/routes/rider.routes.ts           # คนที่ 2
  src/services/planner.service.ts      # คนที่ 2
  src/services/pricing.service.ts      # คนที่ 2
  src/services/routing.service.ts      # คนที่ 2

frontend/src/app/
  pages/overview/                      # คนที่ 3
  pages/customers/                     # คนที่ 3
  components/route-map/                # คนที่ 3
  pages/orders/                        # คนที่ 4
  pages/rider/                         # คนที่ 4
  services/customer-api.service.ts     # คนที่ 3
  services/plan-api.service.ts         # คนที่ 3
  services/order-api.service.ts        # คนที่ 4
  services/rider-api.service.ts        # คนที่ 4
```

Frontend ต้นแบบปัจจุบันรวม 4 หน้าจอไว้ใน `workspace.component` ให้คนที่ 3 และ 4 แยกออกเป็น standalone page components ตามโฟลเดอร์ข้างต้นก่อนเริ่มแก้พร้อมกัน ส่วนแผนที่และ store แยกไฟล์อยู่แล้ว

ให้คนที่ 1 ดูแล `backend/src/app.ts` และคนที่ 3 ดูแล router กับรูปแบบส่วนกลางของ frontend ทุกคนส่งการเปลี่ยนแปลงไฟล์ส่วนกลางให้ผู้ดูแลรวม เพื่อเลี่ยงการแก้ชนกัน

**API แบ่งเจ้าของแบบนี้**:

| API | Backend | Frontend ผู้ใช้ API |
|---|---|---|
| `POST /api/auth/login` | คนที่ 1 | คนที่ 3 ดูแลการเข้าสู่ระบบและสถานะร่วม |
| `/api/customers` และ `/api/customers/:id` | คนที่ 1 | คนที่ 3 |
| `/api/orders` และ `/api/orders/:id` | คนที่ 1 | คนที่ 4 |
| `POST /api/orders/simulate` | คนที่ 1 | คนที่ 4; คนที่ 3 เรียก service ร่วมจากปุ่มบนภาพรวมได้ |
| `POST /api/plans` | คนที่ 2 | คนที่ 3 |
| `GET /api/plans/:id` | คนที่ 2 | คนที่ 3 |
| `POST /api/plans/:id/confirm` | คนที่ 2 | คนที่ 3 |
| `POST /api/rider/jobs/lookup` | คนที่ 2 | คนที่ 4 |

**ก่อนแยกไปทำ ให้ตกลงร่วมกันประมาณครึ่งวัน**:

- ใช้ชนิดข้อมูลจาก `models.ts` และแบบฐานข้อมูล/API จากเอกสาร backend เป็นฐาน แล้วตกลงชื่อ field ที่จะส่งจริง
- ล็อกพิกัดร้านและข้อมูลตัวอย่างให้ทุกคนใช้ชุดเดียวกัน
- API ของแผนต้องคืนภาพรวมต้นทุนและใบงานพร้อมจุดส่งเรียงลำดับให้ frontend แสดงได้
- กำหนดหน่วยให้ชัด: ฐานข้อมูลเก็บเงินเป็นสตางค์ ระยะเป็นเมตร ส่วน response จะใช้หน่วยใดต้องระบุในสัญญา API และแปลงใน API service ก่อนเข้าหน้าจอ
- ถ้าใช้ GeoJSON พิกัดเป็น `[longitude, latitude]` ส่วน Leaflet ใช้ `[latitude, longitude]` คนที่ 3 ต้องแปลงให้ถูก
- กำหนด error รูปแบบเดียว เช่น `{ "message": "จำนวนกล่องต้องอยู่ระหว่าง 1–3" }` และกำหนดรหัสสถานะ HTTP สำหรับข้อมูลผิด ไม่พบ และแผนล้าสมัย
- คนที่ 1 เพิ่ม version ของออเดอร์เมื่อแก้ไข และตรวจสถานะเพื่อห้ามแก้หลังมอบหมาย คนที่ 2 ใช้ version ตรวจแผนก่อนยืนยัน และทำการยืนยัน/มอบหมายใน transaction
- การแก้ข้อมูลลูกค้าที่มีผลต่อแผนต้องทำให้แผนฉบับร่างล้าสมัยด้วย เช่น ตรวจ version หรือเปรียบเทียบ snapshot ก่อนยืนยัน
- คนที่ 1 และ 2 ตกลงการเพิ่ม field หรือตารางร่วมกัน ให้คนที่ 1 เป็นผู้แก้ schema

**กติกาที่ทุกส่วนต้องตรงกัน**:

- ออเดอร์ละ 1–3 กล่อง และใบงานละไม่เกิน 3 ออเดอร์
- ออกส่ง 11:30 น. ต้องถึงลูกค้าครบภายใน 12:30 น.
- ค่าเริ่มต้นใช้ความเร็ว 30 กม./ชม. เวลาส่งมอบ 2 นาทีต่อจุด และเผื่อ 5 นาที
- ค่าส่งต่อใบงาน = `15 + 2 × จำนวนกล่องในใบงาน × ระยะทางกิโลเมตร`
- ตัวอย่าง 6 กล่อง วิ่ง 2 กม. ต้องได้ค่าส่งรวม 39 บาท
- ระยะทางเริ่มต้นนับจากร้านถึงลูกค้าคนสุดท้าย ไม่รวมขากลับร้าน
- ต้องมีออเดอร์ครบ ไม่มีงานซ้ำ และห้ามยืนยันแผนที่ยังส่งไม่ครบหรือส่งไม่ทันตามแบบคำนวณ
- การยืนยันแผนซ้ำต้องไม่สร้างใบงานเพิ่ม
- การคำนวณใหม่สร้างแผนฉบับร่างใหม่ เก็บแผนเดิมให้เปรียบเทียบได้ แต่แผนจากข้อมูลเก่าห้ามนำมายืนยัน
- หน้าร้านต้องแสดงกำไรติดลบตามจริงเมื่อไม่มีแผนที่ทำให้มีกำไร
- เลขใบงานไรเดอร์ต้องค้นได้เฉพาะใบงานที่ยืนยันแล้ว ใช้ข้อมูลลูกค้าสำเนาของใบงาน และมีอายุการใช้งานที่กำหนด

**ลำดับการทำงานที่แนะนำ**:

| ช่วง | คนที่ 1 | คนที่ 2 | คนที่ 3 | คนที่ 4 |
|---|---|---|---|---|
| เริ่มต้น | ร่วมกำหนด schema/API | ร่วมกำหนดข้อมูล planner | แยกหน้า overview/customers | แยกหน้า orders/rider |
| พัฒนารอบแรก | DB และ CRUD | Planner และสูตรค่าส่งจากข้อมูลตัวอย่าง | หน้าจอด้วยข้อมูลจำลอง | หน้าจอด้วยข้อมูลจำลอง |
| พัฒนารอบสอง | Auth และ validation | บันทึกแผน ยืนยัน และค้นหาใบงาน | เชื่อม API และแผนที่ | เชื่อม API ออเดอร์และไรเดอร์ |
| รวมระบบ | แก้ API ที่พบปัญหา | ตรวจข้อจำกัดและข้อมูลแผน | ตรวจ flow เจ้าของร้าน | ประสานเดโม flow ไรเดอร์ |
| ก่อนส่ง | เขียนส่วนฐานข้อมูล/API | เขียนส่วนอัลกอริทึมและผลทดสอบ | เขียนส่วนหน้าร้าน/Figma | เขียนส่วนมือถือและรวบรวมคู่มือ |

ทำงานคู่ขนานได้ตั้งแต่ตกลง API โดย frontend ใช้ข้อมูลจำลองระหว่างรอ backend จากนั้นรวมผ่าน Git ทีละส่วนที่ทดสอบผ่านแล้ว

**เดโมร่วมก่อนส่งโปรเจกต์**:

1. คนที่ 1 เตรียมข้อมูลลูกค้าและออเดอร์จำลอง 24 รายการ
2. คนที่ 4 สาธิตแก้จำนวนกล่อง เพิ่มและยกเลิกออเดอร์
3. คนที่ 3 สาธิตข้อมูลลูกค้า พิกัด และกดจัดเส้นทาง
4. คนที่ 2 อธิบายการแบ่งงาน สูตรค่าส่ง และเหตุผลที่แผนผ่านเงื่อนไขเวลา
5. คนที่ 3 เปรียบเทียบและยืนยันแผน
6. คนที่ 4 ใช้เลขใบงานเปิดจากมือถืออีกเครื่องที่เชื่อม backend เดียวกัน ดูลำดับส่งและเปิดแผนที่
7. ทุกคนตรวจร่วมว่าแก้ออเดอร์ที่ยืนยันแล้วไม่ได้ ไม่มีออเดอร์ซ้ำหรือหาย และแสดงต้นทุนตรงกับใบงาน
